# ADR-0002: 流式翻译的 CPU 风暴根因与防复发硬规则

- 状态：**Accepted**（2026-09-04，事故复盘后确立）
- 关联：ADR-0001

## 事故（2026-09-04 上午）

现象：llama-server 单实例 CPU 长期 200%+（≈3.3 核），slots 双槽持续满载、任务号数秒内 +500；TUI 里"已翻译"状态常驻但界面不变。

根因（双 bug 叠加）：

1. **渲染时机错配**：旧设计在 transformer 内做"异步翻译 → 写缓存 → 期待下一次渲染替换"。但 Pi-TUI Markdown 按 `(text,width)` 缓存渲染结果，异步缓存写完**不会**使已渲染消息失效；`setStatus` 只更新 footer —— 译文永远不会异步回填已上屏消息，表现为"界面不变"。
2. **CPU 风暴**：transformer 在流式**每一帧**对整份 markdown 请求翻译；当消息是连续段落（无空行）时，唯一候选段文本随流增长 → 缓存键每帧都变 → 永不命中 → **每个 chunk 都发一次完整翻译请求**（当时 `max_tokens 2048`，单任务 1–3 分钟）→ llama 队列无限堆积、双槽满载烧 CPU。

## 决策（防复发硬规则，任何后续编辑不得回退）

1. **行级稳定切段**：只对**已完结的行**（`\n` 之后）发起翻译；每行独立缓存键（`fnv1a32(line):len(line)`）。终结帧才对剩余行发起。杜绝"整段随流增长、键永变"。
2. **请求去重**：`inFlight` 集合 —— 发起前检查 `cache.has(k) || inFlight.has(k)`，进入前 `add`，`finally` 删除。流式每帧 transformer 重跑也不会重复发同一行。
3. **`max_tokens ≤ 256`**：单行翻译的小输出预算。历史教训：1024/2048 会让退化重复拖长 batch，顶到 Metal/GPU 等待甚至 hang。
4. **llama-server 参数**：`--parallel 2 --ctx-size 4096 --threads 4`（`--parallel 1` 单槽会让多客户端互相串行阻塞；`--ctx-size` 足够容纳行级请求；线程数适配桌面 CPU）。
5. **失败隔离**：单行失败只丢弃该行（服务仍在线时）；仅探活确认服务真挂才触发重启（看门狗带 ≥30s 冷却）；绝不因一次空响应清空队列/缓存/面板。
6. **客户端并发上限（v6 增补）**：`inFlight` 同时上限 8（`MAX_STREAM_INFLIGHT`），满载丢弃、终结帧/message_end 兑底重试 —— 流式帧/秒 × 行/帧的请求速率上限受双保险（客户端上限 + 服务端 `--parallel 2` 队列）约束。

## 验证

- 单测（harness）：无换行增长只入队 1 次；多行追加每行一次；超长终结帧只 1 次；缓存命中跳过。
- 压测（真实服务）：8 并发线性排队 ~150–700ms，服务不崩、不堆积。
- 事后观察：新实现空闲 CPU 0.1%，无任务堆积。
